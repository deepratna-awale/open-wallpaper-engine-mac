# Architecture

Open Wallpaper Engine for macOS plays Wallpaper Engine (WE) wallpapers: **scene**, **video** and **web**. The `application` type is out of scope. The goal is to run *any* WE wallpaper, including arbitrary Workshop scenes with custom effects, shaders and SceneScripts. So the scene engine implements WE's actual formats and semantics, not per-wallpaper approximations.

This document describes the target structure and the rules for what goes where. [`docs/reorg-plan.md`](reorg-plan.md) lists the steps from today's layout to this one. [`docs/progress-snapshot.md`](progress-snapshot.md) records how complete each feature is. [`docs/optimizations.md`](optimizations.md) records what was tried to make wallpapers cheaper, what shipped and what was rejected.

## Big picture

```
┌──────────────────────── App shell (SwiftUI/AppKit) ────────────────────────┐
│ App/  Library/  Workshop/  Settings/  UI/            (views + view models) │
└───────────────┬───────────────────────────────┬────────────────────────────┘
                │ WEWallpaper                    │
      ┌─────────▼─────────┐  ┌─────────────┐  ┌──▼──────────┐
      │ Scene/  (engine)  │  │ Video/      │  │ Web/        │
      │  Format  → Values │  │ AVPlayer +  │  │ WKWebView + │
      │  Shaders → Render │  │ music sync  │  │ WE web API  │
      │  Scripting, Audio │  └──────┬──────┘  └─────────────┘
      └─────────┬─────────┘         │
                └──────────┬────────┘
                    ┌──────▼──────┐
                    │ Audio/      │  system capture (process tap or SCK), item taps
                    └─────────────┘
Core/  logging, diagnostics, settings store, asset locations: usable by everything above
```

**Dependency direction:** arrows only point down. Code in `Scene/` must never import or reference anything in `UI/`, `Library/`, `Settings/` views or `AppDelegate`. Code in `Core/` depends on nothing else in the app.

## Targets

- **`OpenWallpaperEngine.framework`** (target OpenWallpaperEngineFramework, module `OpenWallpaperEngine`): all of the app's code, the folders below, with the packages it uses (ShaderToolchain, Sparkle, OWEEditor, OWEControlProtocol, OWETheming). It is embedded once, in the app's `Contents/Frameworks`. The code's own resources are in the framework's bundle and read through `AppBundleLayout.framework`: the Metal library (`SceneMetalLibrary`), SceneScript's JavaScript, the now-playing adapter, the placeholder media and the legal documents. Objective-C goes through the framework's umbrella header (`OpenWallpaperEngine.h`), not a bridging header.
- **Open Wallpaper Engine.app** (target OpenWallpaperEngine) and **Wallpaper Editor.app** (target WallpaperEditor, embedded in `Contents/Helpers`): small executables, the same `OpenWallpaperEngineApp/main.swift`, which calls `AppMain.run()`; the bundle id says which app it is. Each app's bundle (`Bundle.main`) keeps what belongs to the app: its Info.plist, icon, asset catalog and `Localizable.xcstrings`, which SwiftUI, AppKit and `String(localized:)` look up there. The editor finds the framework through its rpath, `@executable_path/../../../../Frameworks`.
- **owe-mcp** (target OWEMCPServer, embedded in `Contents/Helpers`): the MCP Server plugin's command-line server, linking only `Packages/OWEControl` and system libraries (see [`MCP/`](#mcp-packagesowecontrol-and-mcpserver-control-by-mcp-clients)).
- **Tests** (`OpenWallpaperEngineTests`) link the framework (`@testable import OpenWallpaperEngine`) and run hosted in the app.

## Modules

These are folders in the framework target today. The scene engine (`Scene/`, `Audio/`, `Core/`) is meant to become a local Swift package (`Packages/WEScene`) during Phase 2, so it can be unit-tested and run headless. Keeping the dependency rules now is what makes that extraction a move rather than a rewrite.

### `Core/`: shared infrastructure

- **Logging and diagnostics:** `OWELog`, signposts and frame metrics.
- **Settings:** the global settings model and store.
- The **WE assets location**.
- The **Objective-C exception catcher**.
- It must not reference UI, view models or `AppDelegate`.

### `Scene/`: the WE scene engine

| Area | Responsibility | Examples |
|---|---|---|
| `Scene/Format/` | Decode WE files into plain Swift models. It does no rendering and has no side effects. | `scene.json`, `project.json` scene properties, `effect.json`, materials, models, particles, `.pkg`, `.tex` |
| `Scene/Values/` | Resolve every dynamic value the same way: literal, `{"user":…}`, `{"user":{"name","condition"}}`, `{"script":…}`, `{"animation":…}`. User bindings live in one table per loaded scene (`Values/Bindings`). | `UserPropertyBindingTable`, `SceneValueSource` |
| `Scene/Shaders/` | GLSL → SPIR-V → MSL translation (in a helper process, `--shader-compile-helper`), reflection, the translation cache and the effect catalog. | `ShaderVariantTranslator`, `HelperShaderCompiler`, `ShaderCompileHelperServer`, `InProcessShaderCompiler`, `SceneDynamicEffectCatalog` |
| `Scene/Rendering/` | Metal: layers, the effect pass graph, render targets, text, particles and the camera. | `SceneMetalRenderer`, `SceneShaders.metal` |
| `Scene/Scripting/` | The SceneScript runtime (JavaScriptCore), one per wallpaper instance on its own thread, and the WE JS API surface as extensions; `Host/` ties a runtime to the renderer (docs/scenescript-plan.md). | `SceneScriptRuntime`, `SceneScriptWallpaper`, `SceneScriptSceneMirror` |
| `Scene/Loading/` | Turns a wallpaper into render content: loads, resolves and builds. | `SceneWallpaperViewModel` (to be split) |
| `Scene/UI/` | Scene-specific SwiftUI: the Scene Editor (Live) and user properties, and the isolated sessions its export modes edit. These are the **only** scene files allowed to import SwiftUI views. | `SceneInspectorView`, `SceneUserPropertiesView`, `SceneHelp`, `IsolatedSceneEditSession` |

### `Audio/`

- System audio capture (a Core Audio process tap on macOS 14.2+, ScreenCaptureKit before or as the fallback) with a restart lifecycle.
- Per-player taps (`AudioLevelTap`).
- Spectrum and waveform snapshots.
- One producer, many consumers: scene shaders, SceneScript `registerAudioBuffers`, video music sync.

### `Video/` and `Web/`

- Each holds its player, view, view model and type-specific features: video music sync, and the web wallpaper property/audio bridge.
- **`Web/Chromium/`:** the optional Chromium engine (CEF), installed on demand and pinned by SHA-256. CEF runs only in the `owe-chromium-helper` XPC service (target `OWEChromiumHelper/`), never in the app, and its frames reach the app as IOSurfaces. See [`docs/chromium-engine.md`](chromium-engine.md).
- **Web engine routing:** WebKit by default; Chromium only for a wallpaper that needs it (a Chromium-only API found) while the engine is installed, or when the wallpaper's override says so (`WebEngineRouting`). `WebWallpaperViewModel` drives either engine through `WebWallpaperPage` (a `WKWebView` or a `ChromiumBrowserPage`), so the WE bridge is one implementation. Without Chromium, `ChromiumFeatureAdvisor` points out wallpapers that use Chromium-only APIs (static scan plus WebKit's runtime probe).

### `Library/`, `Workshop/`, `Settings/`, `UI/`, `App/`

- **`Library/`:** app-shell features. It holds the wallpaper library model and the import paths (`WEProject`, `WallpaperDirectory`, zip/pkg import).
  - Installed lists what WE lists (`InstalledLibrary`): items whose project.json `type` is scene, video, web or application. Asset items (`"category": "Asset"`, no `type`) and items downloaded only as another wallpaper's dependency (`WorkshopDependencyIndex`, a hidden file in the library folder) stay on disk, where `WorkshopAssetResolver` finds them, but aren't listed. Downloading such an item yourself makes it yours and lists it.
  - Library folders (Settings › Assets › Library Folders, `LibraryFolders`) are more folders of wallpaper folders the Installed tab lists after the storage folder's: only folders with a project.json, and a Workshop item already listed from an earlier folder isn't listed again. They are read only: nothing is downloaded or moved into them. `LibraryFolderWatcher` lists their changes as they happen.
  - Deleting a wallpaper removes the dependency-only items nothing left in the library references (`WorkshopDependencyCleanup`, logged). WE leaves required items to Steam, where the user can still see and unsubscribe them; here they are hidden, so keeping them would leave them on disk with no way to remove them.
- **`Workshop/`:** steamcmd and the Workshop API. Steam secrets live in the keychain (`Core/Keychain`, `SteamCredentials`): the Web API key and the steamcmd account name. The password and Steam Guard code are piped to steamcmd on stdin and never stored; steamcmd keeps its own login token. The API key goes in the `x-webapi-key` header, never a URL.
  - Every download lands in the Wallpaper Storage folder as `<storage>/<id>` (`WorkshopItemInstaller`): steamcmd's `force_install_dir` is a hidden `.owe-steamcmd` folder inside it, the finished item is renamed into place and the staging folder deleted. A preview the user applies moves from the preview cache into storage the same way (copied into a hidden folder there, then renamed). A storage folder on a disconnected volume fails the download with that reason; nothing falls back to another folder. steamcmd runs through `SteamCmdRunning`, so tests use a fake.
  - Discover (`WorkshopDiscover`) is WE's static explore lists (`getStaticExploreQueries` in its UI) as the same keyed QueryFiles requests: WE's trend sorts are RankedByTrend with its `days`, and the `Wallpaper` and `Everyone` tags WE adds to every list are sent as exclusions of their siblings, since QueryFiles can't AND required tags. Each list pages on as it scrolls (`WorkshopDiscoverViewModel`).
  - Blocking (`WorkshopBlockList`) is local: blocked items and authors are left out of the Workshop and Discover results. Report opens the item's page in the Steam client or the browser (`WorkshopPageLink`), where the user reports it; nothing is ever posted to Steam for them. "Related Wallpapers" lists the author's items or the presets that require a wallpaper (QueryFiles `child_publishedfileid`).
- **`Installs/`:** what the optional on-demand installs share (the Chromium engine, `Web/Chromium/ChromiumEngineInstaller`, and the depth model, `DepthMaps/DepthMapPluginInstaller`). `VersionedInstallStore` downloads each pinned file, checks its SHA-256, stages the install and renames it into place, keeping the active and the previous version (`VersionedInstallState`); `VersionedInstaller` is the main-actor side (phase, progress, cancel, remove) and `VersionedInstallFailure` the messages for being offline, an HTTP error and a full disk. Each installer keeps only its URLs and files, its install folder and its own step (unpacking the engine, compiling the model).
- **`Settings/`:** settings pages.
- **`UI/`:** the main window and shared components.
- **`App/`:** the entry point, `AppDelegate`, windows and menus.
- Each view model lives next to its view.

### `Editor/` and `Packages/OWEEditor`: the Wallpaper Editor

- The editor ([`docs/editor-plan.md`](editor-plan.md)) is a local Swift package with three modules: `OWESceneEditing` (Foundation only: the edit overlay over scene.json, the layer outline, gizmo and canvas math, `SceneEditSession` with undo, Save as Local Wallpaper), `OWEInspectorKit` (controls the Scene Editor (Live) shares with it) and `OWEEditor` (the window's views and their own string catalog). The package depends on nothing in the app; its tests run with `swift test`.
- `Editor/` is the app's side: the window (`WallpaperEditorController`), whose canvas is the wallpaper's own instance in a preview `WallpaperViewModel`, and the services the module asks for (the user properties view, WE's blend modes, effect help, saving a copy).
- The editor is an **app of its own** inside the app, `Contents/Helpers/Wallpaper Editor.app` (bundle id `<app id>.editor`, target WallpaperEditor, a small executable running the app's framework, `Core/AppBundleLayout`), launched with `--wallpaper-editor <folder>` (`App/Launch/AppLaunchMode`, `AppLaunchPlan`); its delegate (`Editor/Process/WallpaperEditorAppDelegate`) starts none of the main app's launch services and never makes `AppDelegate.shared`. The app launches it through LaunchServices, or asks the running one to open a wallpaper, over the session's distributed notifications (`AppProcessChannel`: a name and a folder, at most with an undo step's name or a timeline command; never the edits). What the editor saves reaches the app's instances through `Editor/Sync/WallpaperEditorChangeSync` (messages plus a watcher on the overlay folder), which posts the same in-process notifications as before. See [`docs/editor-plan.md`](editor-plan.md), "Separate process".
- Edits are an overlay per wallpaper (`<supportDirectory>/editor/<identity>.json`, `Scene/Loading/SceneEditOverlayFiles`), never written into the wallpaper, with the files the editor added beside it (`<identity>.assets`, `EditorAssetStore`), which the scene loader reads after the wallpaper's own (`SceneWallpaperViewModel.wallpaperData`). `ScenePreparation` applies the overlay (layers added, deleted and reordered, effects added and reordered, every field and effect value) before the Scene Editor's edits, and the scene cache key covers it.
- A change of values the renderer takes per frame (a layer's transform, opacity and colour, an effect's visibility and constants) is drawn live: the instance measures the editor's overlay against the one its scene was read with (`SceneEditLiveValues`, `SceneWallpaperInstance+EditorLive`) and the renderer applies the difference (`SceneEditorLive`: transforms like user bindings, effect constants as writes under the scripts'). Anything else reloads every running instance of the wallpaper.
- Scripting and user-property authoring (P6) live in `Scripting/` and `Properties/` subfolders of `OWESceneEditing` (the overlay's `SceneAuthoring`, the SceneScript typings and autocomplete, the syntax check, templates, `UserPropertyDraft` and its conditions) and of `OWEEditor` (the script editor, binding sheet, property editor and preview); the app's `Editor/Scripting/SceneScriptConsoleTap` hands the runtime's console lines and errors to an open editor.
- The particle editor (`Particles/` in both modules) keeps particle definitions and materials it wrote in the overlay; the view model reads them before any file (`setEditorAssets`), and a change of those documents alone rebuilds only the particle objects that read them (`particleObjectIDs(using:)`, `rebuildObjects`) instead of reloading the scene.
- Depth maps (`DepthMaps/` in the app and in both modules, [`docs/depth-maps.md`](depth-maps.md)): one `DepthMapGenerator` per process runs the plugin's Core ML model off the main thread and releases it after five idle minutes; both editors' Depth Map section writes the map and WE's Depth Parallax effect into the wallpaper's editor overlay (the Scene Editor (Live) through an edit session of its own), so the two share them.

### `MCP/`, `Packages/OWEControl` and `MCPServer/`: control by MCP clients

- The **MCP Server** plugin (Settings › Plugins, `MCP/MCPServerPlugin`), off until installed. Installing copies the app's `Contents/Helpers/owe-mcp` (target OWEMCPServer, `MCPServer/main.swift`) into `<supportDirectory>/Plugins/MCP` with an `install.json` naming the app, and opens the control socket; removing closes it and deletes the folder. See [`docs/mcp.md`](mcp.md).
- `Packages/OWEControl` depends on nothing in the app. `OWEControlProtocol` (linked by the framework and by `owe-mcp`) is the control channel: newline-delimited JSON requests and responses with a version, over a Unix domain socket at `<supportDirectory>/Control/control.sock` (folder `0700`, socket `0600`, peers checked with `getpeereid`), which an isolated copy keeps in its own support folder. `OWEMCP` (only `owe-mcp`) is the MCP server: JSON-RPC over stdio, the tools' schemas and argument checks, and starting the app when no socket answers.
- The app's side: `ControlRequestRouter` checks a request's parameters and resolves wallpapers, displays and playlists; `AppControlModel` (behind the `ControlAppModel` protocol, which tests fake) does what the app's own controls do, on the main actor. `owe-mcp` never reads or writes the app's state itself. The other areas are request groups (`ControlRequestGroup`): `MCP/Scene` (the editors), `MCP/Library` (playlists, metadata, displays, settings, plugin status) and `MCP/System` (Live Photo export, the screen saver, the lock-screen picture), each behind a protocol its tests fake.
- **Headless edit sessions.** A client edits a scene through `HeadlessSceneEditService`: one `HeadlessSceneDocument` per wallpaper holds a `SceneEditSession` over the wallpaper's editor overlay with its own undo stack, applies `scene_apply_edits` lists all or nothing as one undo step (on a copy of the session first, through the same session calls as the editors' controls, `SceneEditOperations`), and saves and applies each change as the Wallpaper Editor's window does. `WallpaperEditorChangeSync` announces the save to the editor's process (`app.overlayDidSave`), whose open window of the wallpaper takes it as an undo step (`WallpaperEditorController.adoptSavedOverlay`); a save made elsewhere starts the document over with a fresh undo history.

### `Theming/` and `Packages/OWETheming`: macOS in the wallpaper's colour

- Settings › General › Theming ([`docs/theming.md`](theming.md)): the main display's wallpaper's scheme colour (or its picture's main colour) for the menu bar, the accent and highlight colours, the tinted icon style and the folder colour.
- `Packages/OWETheming` depends on nothing in the app (Foundation, Core Graphics, ImageIO): the colour and OKLab, the accent palette, the menu bar strip's geometry and drawing, the preference values, and `SystemThemeApplier`, which saves the user's values before the first change and restores them. Every write goes through `SystemAppearanceWriter`; its tests use a fake, and an isolated copy of the app a writer that never writes.
- `Theming/` is the app's side: `ThemingController` (when to apply, debounced; owned by the app's delegate) and `DesktopPictureTheming`, the one hook in the per-display desktop pictures `DesktopPictureSync` draws (the menu bar strip).

### `Resources/`

- `Assets.xcassets`, `Localizable.xcstrings`, media.
- No Wallpaper Engine files ship in the repository or the app. `Core/WallpaperEngineAssets` resolves them at runtime: a WE install the user chose, else the cache in the Wallpaper Storage folder (`<storage>/.owe-assets`, filled by `Workshop/WallpaperEngineAssetsService` from the user's Steam copy through SteamCMD), else none (scenes show that they need them). Tests read them only from `OWE_ASSETS`.

## Scene data flow

1. **Load.** `Scene/Format` decodes `project.json`, `scene.json` (from disk or the `.pkg`, with the Wallpaper Editor's overlay and the Scene Editor (Live)'s edits applied, `ScenePreparation`), then models, materials, effects and textures (`.tex`).
2. **Resolve.** `Scene/Values` binds user properties (per wallpaper), scripts and animations to typed values. Nothing downstream reads raw JSON or string-keyed dictionaries.
   - Every `{"user": …}` of scene.json and of every JSON document the build reads (effects, materials, particle systems, models, Workshop dependencies, WE's assets) is recorded in the scene's `UserPropertyBindingTable`, with its path, the typed target it drives and a class: `uniform` (a shader constant, updated in place), `object` (a transform, colour, visibility, particle override or script-read value: the object's state updates) or `structural` (a combo, texture, size or anything unrecognised: the object is rebuilt alone, `SceneObjectReplacement`). The parsers decode the table's resolution of each document, so none can drop a binding.
   - A property change is looked up in the table (`SceneBindingUpdate`). The owners it touches move to a new binding revision (`SceneBindingRevisions`), which every cache of a bound value keys on. Only the app's own keys, scene-wide structure (`general`) and objects the scene's stages hold (lights, sounds, models, cameras) rebuild the content; editing properties ends with one rebuild, the reconcile.
3. **Build.** `Scene/Loading` produces render content: an ordered layer list in authored object order. Each layer carries its full parent transform, its effect pass graph (from `effect.json` passes, `fbos`, `bind`, `target` and combos) and its text, particle and sound state.
4. **Render.** `Scene/Rendering` executes the pass graph each frame through translated WE shaders. Uniforms come from reflection, plus built-ins such as `g_Time`, resolutions, pointer and audio spectrum, plus resolved constants.
5. **Script.** `Scene/Scripting` runs once per frame in one context per wallpaper instance, on its own thread. Layer objects read and write a shared object table; the renderer feeds it each object's drawn values before the frame and draws what scripts wrote after it (`SceneRendererScripts`).

## Wallpaper instances

A wallpaper runs **once**, however many displays show it with the same user properties.

- **The registry.** `WallpaperInstanceRegistry` (`Core/`) holds the running instances, keyed by `WallpaperInstanceKey` (the wallpaper's folder, file and type, and the user-property store it runs with). It belongs to the `WallpaperViewModel` whose displays show them (`sceneInstances`, `videoInstances`), so the Workshop preview window runs its own. Each display holds its instance through a `WallpaperInstanceLease`; the instance stops when no display holds it, one main-queue turn after the last release, so a display that is rebuilt (screens changed) takes hold again first and the wallpaper keeps running. `WallpaperView` keys a display's view by its instance key (`WallpaperViewModel.instanceKeys`), so a display switched to another wallpaper, or to other properties, splits off into that instance.
- **User properties per display.** As in WE, the same wallpaper on two displays has independent user properties (`WallpaperPropertyScope`): each display has its own store (`SceneUserProperties.<identity>.display.<id>`, started from the shared `SceneUserProperties.<identity>`). Settings → General → "Sync properties across displays" (off by default, WE's "Wallpaper per display") makes every display use the shared store. `WallpaperPropertyGroups` regroups the displays when a wallpaper, the setting or saved properties change: displays of a wallpaper whose stores are equal share one instance (the first display's store), a display whose properties differ runs its own. The sidebar and the inspector edit the selected displays' stores (`WallpaperPropertyTargets`); the running store of an instance is `WallpaperPropertyScope.runtimeKey`. AVKit videos have no properties and keep one player per video.
- **Scenes** (and videos on the Metal path): `SceneWallpaperInstance` owns the loader, one `SceneMetalRenderer` (scripts, particles, timelines, effect graph, sound layers) and the observers. Each display is a `SceneWallpaperPresenter` with its own `MTKView`. With one display the renderer draws straight onto it. With several, the display with the highest frame rate drives (`SceneFrameSchedule`; another takes over if it stops drawing): `renderShared` renders the frame once, at the largest scene target any display needs (`SceneViewport`), through the post-process onto a finished frame; every display then `present(in:)`s it with its own size and placement, one copy pass. The cursor is read from the display it is on, through that display's placement.
- **Loading snapshots.** While a scene loads, each display shows a full-resolution picture of the scene's own frame (`ScenePreviewPlaceholder`), crossfaded to the live scene once it draws: the snapshot for the display's pixel size, else the nearest size scaled, else the Workshop preview. `SceneLoadingSnapshotStore` keeps them as HEIC (JPEG where HEIC can't be written) under `<Caches>/Open Wallpaper Engine/LoadingSnapshots`, keyed by the wallpaper's folder, the display's pixel size and a hash of the folder's top-level files, capped as an LRU. The prepare-on-arrival helper (`--prepare-wallpapers`) writes one per connected display after a second of scene time; a running scene (`SceneLoadingSnapshotCapture`, driven by `SceneRenderLoop`) refreshes its display size once per session, and again after its user properties change, reading the frame back off the render thread. Deleting a wallpaper removes its snapshots.
- **AVKit videos:** one `VideoWallpaperViewModel` (one decoding player, one audio player) per video; each display's `AVPlayerView` shows the shared player.
- **Web:** a `WKWebView` can't be in two windows, so each display keeps its page, a clone's and a stretch's displays too ("Display layouts"). Only the page on the wallpaper's audible display plays sound; the others are muted (`WebPageAudio`).
- **Sound** (`WallpaperAudioRouting`): each running wallpaper plays its sound once; a web wallpaper's from its audible display (the main display when it shows it, else the lowest display id), and a wallpaper running as several instances (different properties) from the instance on that display. Different wallpapers on different displays each play theirs. Settings → Audio Output silences all of them; volume and mute (the status menu) apply to all.
- **The watchdog** gets one frame time per rendered frame of an instance, not one per display.

## Display layouts

WE's multi-monitor model (`Library/DisplayLayout/`, the Displays sheet). How to use it: [`display-layouts.md`](display-layouts.md).

- **The layout** (`DisplayLayoutConfiguration`, WE's `wallpaperconfig.layout`, saved in the app's defaults as `DisplayLayout`): a wallpaper per display (0, the default, so per-display wallpapers saved before layouts show as they did), one wallpaper stretched over every display (1, from the main display's selection) or one wallpaper cloned onto every display (2).
- **Groups** (`DisplayGroup`, WE's `profile.groups`), under a wallpaper per display only: a stretch or clone group of some displays beside the others' own wallpapers. Its id is `group_` and an FNV-1a hash of the members, the same on every launch. Displays are named by identity (`DisplayIdentity`: the UUID macOS derives from the display's vendor, model and serial number), not by id. A group with fewer than two connected displays is dormant: kept, and back when its displays are; removing a display from a group of two removes the group.
- **Resolution** (`DisplayLayoutResolution`): the layout on the connected displays, by display id: each clone or stretch member's source display (a clone's main clone display: the chosen one, else the group's first member, under the clone layout the main display; a stretch's first connected member), each stretched display's canvas, each split display's regions, the flipped and the muted displays, and the groups the sheet outlines (a stretch solid, a clone dashed).
- **Clone.** A member shows its main display's wallpaper through the same running instance (`refreshInstanceKeys` gives it the main display's key, and `propertyScope(for:)` its properties), so a scene renders once at the largest target its displays need and each presents it at its own size and placement, an AVKit video has one player (one decode) with a view per display, and a Metal video is one scene. A wallpaper set on a member is set on its main clone display, so the whole clone shows it. A member's own selection stays as it was (WE keeps each monitor's `selectedwallpapers` under a clone): `wallpaper(for:)` resolves what a display shows, and leaving the clone (back to a wallpaper per display, the group removed, or the member taken out) shows the member's own wallpaper again. Web pages and WebM videos keep a page per display: no public API shows one live `WKWebView` in two windows (a `CALayer` has one parent; snapshots read the page back on the CPU every frame), so a clone of a web wallpaper costs what two displays of it cost before.
- **Flip** (WE's "Flip clone display"): the window's content is mirrored by a layer transform (`WallpaperWindowContentView`), so the compositor mirrors the frame the display shows and nothing renders again; a scene reads the cursor mirrored there (`NSView.isMirroredOnScreen`). The main clone display can't be flipped, so one member always shows the wallpaper as it is.
- **Mute** (per display, as in WE): a muted display's playback becomes `.mute` (`WallpaperViewModel.displayPlayback`, merged with the playback rules' `rulePlayback`), so a wallpaper's sound (and, for a web page, which display's page plays it) comes from a display that shows it unmuted, and goes quiet when none does (`DisplayPlaybackRouting`). Audio-reactive input is the system's output, as in WE, and stays on.
- **Stretch** (WE's span: the stretch layout and stretch groups). The canvas (`DisplayCanvas`) is the bounding box of the members' desktop rects in global points, as WE's `ui.js` sizes a group: gaps between displays are canvas no display shows, and there's no bezel or density compensation, so each display shows its own rect of the one canvas. Members run the source's instance, as in a clone.
  - *Scene:* the window's content names the canvas (`WallpaperWindowContentView.stretchCanvas`, read into `SceneViewSnapshot.canvas`). A stretched display's `SceneViewport` is the whole canvas at the display's density, so `renderShared` renders one frame for the canvas, at the densest member's pixels (the GPU's largest texture is the only cap, `SceneRenderResolution`), even with one member showing; each display presents its rect (`SceneCanvasSpan`: the frame placed on the canvas, moved by the display's offset, one copy pass). The cursor and parallax read the cursor on the canvas from the display it is on (`SceneViewSnapshot.canvasCursor`), and scripts see the canvas as the screen. A stretched display's picture isn't a loading snapshot.
  - *Video (AVKit):* one player (one decode). Each display's player view is sized to the canvas and offset in its window, which clips it to the display (`View.stretched(on:display:)`): the compositor samples only the display's part. (An `AVPlayerLayer`'s `contentsRect` doesn't reach its video sublayer, so the offset frame does what it would.) A Metal video is a scene.
  - *Web and WebM:* a page can't be one view in two windows, and drawing one offscreen page and copying snapshots of it reads every frame back on the CPU, so each display keeps its own page, sized to the canvas and offset like a video: each page lays out and draws the whole canvas, and only its display's part is composited. The pages start together; a page that animates by the clock stays in step, one that keeps its own random state doesn't. On two 1920×1080 Retina displays a stretched page costs about 30 % more CPU and GPU and 50 % more memory than the same page on each display (each page draws twice the area); a stretched scene draws one canvas-sized frame, about 30 % more than one frame for both displays.
- **Splits** (WE's `profile.splits`, under a wallpaper per display, on displays in no group): `{direction, position}` per location, a display's identity or a region's (`<identity>/L`, `/R`, nested), `direction` 0 (WE's "Vertical") side by side and 1 one above the other, `position` the fraction of the width or height from the left or top. `DisplaySplitLayout` divides the display into regions in whole points. Each region is a display of its own, id `<display id>/L…` (`DisplayLayoutResolution.regions`): its own wallpaper, properties and view (`DisplayWallpaperView` lays the regions out in the display's window), its display's playback, mute and enabled state (`routedScreens`). A wallpaper set on a split display goes to its regions; the first region of a new split takes what the display showed, as in WE. WE has no depth limit; its only limit, kept here, is a divider at least a point inside its region (`DisplaySplit.clampedPosition`). A stretch group removes its displays' splits, as WE's does.
- **Profiles** (WE's "Save profile" / "Load profile", `DisplayProfiles`): a named copy of the whole layout (layout, groups, splits, flips, mute) and each display's and region's selection, by location, saved as JSON in Application Support (`DisplayProfiles.json`). `DisplayProfiles.load(name:)` is what an app rule's "Load profile" action calls.
- **Screen saver layout** (`ScreenSaverDisplayLayout`, WE's `wallpaperconfigscreensaver = {layout, sameaswallpaper}`, saved as `ScreenSaverDisplayLayout`): "Same as wallpaper" (the default) follows the wallpapers' layout and groups; otherwise a loop per display, one stretched or one cloned. See "Lock screen and screen saver".

## Isolated edits (the Scene Editor (Live)'s Screen Saver and export modes)

- **The session.** A mode that previews and renders its own version of a wallpaper (the Screen Saver and iPhone & iPad Export modes) opens an `IsolatedSceneEditSession` (`Scene/UI/`). It copies the edited store's values (user properties and the Scene Editor (Live)'s layer edits) into an isolated store, `WallpaperPropertyScope.isolated(<purpose>)`, saved under that suffix and run under its own runtime key. The Scene Editor (Live)'s own models are pointed at that scope, so the mode's layer and property edits use the same code as the Wallpaper mode; `setValues` and `setLayerVisible` do the same from code. A save to an isolated store doesn't regroup the displays.
- **The private instance.** `IsolatedSceneView` runs the wallpaper from the session's own `WallpaperInstanceRegistry` under `WallpaperInstanceKey(wallpaper, properties: .isolated(…))`: never the displays' shared instance, silent (a preview screen), and without loading snapshots, so the desktop's snapshots and lock-screen picture don't change.
- **The render hook.** `values` is everything an offscreen render of that version takes: the Live Photo job's properties (`LivePhotoJob`) and the screen saver recording's (`ScreenSaverPlugin.Target.properties`), rendered by the helper with exactly these. `replaceValues` swaps the whole store for a mode's own saved version (the Screen Saver mode's choices).
- **Lifetime.** Leaving the mode, closing the Scene Editor (Live)'s window or showing another wallpaper ends the session: the isolated store is removed and its running store emptied.

## Live Photo export (`LivePhoto/`)

How to use it: [`iphone-ipad-export.md`](iphone-ipad-export.md).

- The iPhone & iPad Export mode frames the private instance as the chosen device's lock screen (`DeviceModel`, `LockScreenLayout`, `LivePhotoCrop`); the Export Settings (`LivePhotoExportSettingsView`) are its panel and the sheet before an export.
- The helper run `--render-live-photo <job.json>` (`LivePhotoRenderer`) renders offscreen through the real loader and renderer. A motion job renders the first 8 s small and writes each frame's difference from the last (`LivePhotoMotion`, `ScreenSaverFrameSignature`); the app moves the clip to the window with the most motion. An export renders the clip into a near-lossless intermediate movie while choosing the still (`LivePhotoKeyFrame`), writes the HEIC, then encodes the movie (`LivePhotoMovieEncoder`, `IntermediateReader`) with the still-image-time track at the still's frame and the screen saver's crossfade into the still at both ends.
- With "Also Save to Photos Album" on, the pair goes into a regular Photos album through PhotoKit (`LivePhotoAlbumSync` over `LivePhotoLibrary`, `PhotoKitLibrary`).

## Android export (`AndroidExport/`)

WE's "Export .mpkg" for its Android app ("Export for Android…" in the library's context menu and the Details panel, for one wallpaper or a selection; `export_android` for MCP clients). Ground truth is WE 2.8.42's exports (`we-test-wp-images`, `android-transfer/MPKG.md`), which the WE app on a tablet imports and plays. How to use it, and Send over Wi-Fi's security: [`android-export.md`](android-export.md).

- **The container** (`Scene/Format/MobilePackageWriter`): scene.pkg's layout with the magic `PKGM0014`, unencrypted, entries sorted by their paths' bytes; `PKGParser(magic: "PKGM")` reads it. Re-packing WE's Dynamic sample from its own entries gives its bytes exactly (`MobilePackageTests`).
- **WE's JSON** (`Scene/Format/WEJSONDocument`, `WEJSONWriter`): the files WE writes again (scene.json, a changed project.json) are JsonCpp's styled output: tab indents, `" : "`, sorted members, short scalar arrays on one line, reals at 8 significant digits with `.0` on whole numbers, `\uxxxx` for non-ASCII, CRLF, no final newline. Integers and reals keep the kind the source had.
- **What goes in** (`AndroidPackageBuilder`):
  - *Video:* the video file byte for byte, its preview, and a project.json of `file`, `preview`, `title`, `type: "video"`.
  - *Scene, Dynamic (High Quality, Balanced):* every file of the scene.pkg (or the folder) but its sound files (WE leaves the music out; the sound layer keeps naming its file), project.json and the preview as they are; scene.json written again with `general.texturereduction` (1, 2 or 4: the quality button's preset from WE's table, `browseMobileUploadModalCtrl`'s `high`/`medium`/`low` × `pixel`/`normal`/`uhd`, whose column is `AndroidExportOptions.ResolutionClass`: a resolution tag over 1920×1080 is `uhd`, scenes all under 640×480 `pixel`; so a 4K scene's Balanced writes 4); shaders made GLSL ES-safe as WE does (`MobileShaderCompatibility`: `sample` → `_sample`, whole-number literals in float constructors and float declarations' arithmetic → floats); `.tex` files converted (`MobileTextureConverter`): R8/RG88 unchanged, raw RGBA8888 re-containered (`TEXB0004`), pictures and DXT decoded, reduced, padded to 4×4 blocks and stored as one ETC2 RGBA8 mipmap (format 5, `ETC2Encoder`, LZ4 `LZ4BlockEncoder`, `TEXWriter`) with WE's header sizes; textures sampled only as a pass's later texture get flag `0x8`. Pixel art keeps every texture full-size, uncompressed RGBA8888 with nearest filtering. Only the ETC2 blocks differ from WE's sample (their encoder isn't ours); every other file, header field and size matches.
  - *Scene, Pre-Rendered (High Performance):* `wallpaper.mp4`, scene.json (`texturereduction` 4, as WE writes it), project.json with `file: "wallpaper.mp4"` (`type` stays `Scene`) and the preview. The video (`AndroidVideoRenderer`, helper run `--render-android-video`, `AndroidVideoJob`) is drawn by the Live Photo export's offscreen render loop (`LivePhotoRenderer.render`) through the crop (`AndroidExportOptions.crop`, a `LivePhotoCrop`: 9:16 at the alignment slider's position, or the whole scene), 30.0 s at the chosen frame rate, the seam crossfaded as the screen saver's loop is (`ScreenSaverSeamFinder.crossfadeWeight`), H.264 Constrained Baseline (CAVLC, BT.709) at ~8 Mbit/s for 1080×1920 at 30 fps, scaled to the pixels per second.
  - Web and application wallpapers are skipped with WE's message; a video over 4 GB too (32-bit offsets).
- **The sheet** (`AndroidExportSheet`, `AndroidExportModel`): WE's dialog. The pre-rendered crop's preview is a private instance in an `IsolatedSceneEditSession` (purpose `android-export`), so the desktop never changes; the previewed scene renders with that session's values, the others with the values the Scene Editor (Live) would copy.
- **The Scene Editor (Live)'s Android Export tab** (`AndroidExport/Editor/`, `AndroidExportEditorModel`; "Edit in Scene Editor…" in the sheet for one scene; `editor_set_tab` `android_export`): the iPhone & iPad Export's tools on an `IsolatedSceneEditSession` (purpose `android-export-editor`): the layer controls and user properties, the crop with the pinned preview (`LockScreenPreview.layout`, `pinned`), the parallax pad, Export Settings as a panel and as a sheet, framed as an Android screen with a status-bar guide (`AndroidScreenPreview`). Devices come from `AndroidDevice.table` (each with its spec page), or a custom width × height (320…8192, `AndroidCustomSize`); a tablet can be turned. Dynamic (Balanced) is the tab's default, as in the sheet. Pre-Rendered renders the session's values through the tab's crop and pointer (`AndroidVideoFraming` on the item, the pointer in `AndroidVideoJob`) at the screen's pixels or a preset size, the frame rate and length chosen, the bit rate scaled with the pixels. Dynamic bakes the session's values into the package (`AndroidSceneBake`): object JSON, origin, scale and visibility, effect visibility, constants and combos into scene.json (a user-bound value keeps its binding, an animated one its animation), a replaced file's JSON as that file, and each declared user property's value as project.json's default.
- **Batches** (`AndroidExportPlan`, `AndroidExportQueue`, `AndroidExportBatch`): a selection becomes items (scenes share the options, each can have its own mode) and skipped wallpapers with their reasons; names are `<title>.mpkg`, unique within the batch and the folder (`AndroidExportNaming`). Pre-renders run one at a time (the GPU), file-only work two at a time beside them; cancelling stops what runs and leaves the rest. The batch lists the packages in the selection's order with their title, type, mode, size and preview, for a later step to send.
- **Send over Wi-Fi** (`AndroidExport/WiFi/`): after an export (and from the sheet's "Send over Wi-Fi…" button) a sheet (`AndroidWiFiSendSheet`, `AndroidWiFiSession`) serves the batch to the phone's browser; `android_send_wifi` starts the same session for MCP clients, without the sheet.
  - *Server* (`AndroidWiFiServer`, `AndroidWiFiConnection`, `AndroidWiFiHTTP`): a Network.framework `NWListener` speaking minimal HTTP/1.1 (one GET per connection, then close), bound to one local-network IPv4 address (`AndroidLANAddress`: private or link-local addresses of interfaces that are up and not loopback or point-to-point; the primary interface's first, a picker for the others). It accepts only peers on that subnet (`acceptLocalOnly`, then checked again), never cellular. IPv6 isn't offered: a link-local URL needs a zone Android's browsers don't take. No Bonjour. The app isn't sandboxed; a sandboxed build needs `com.apple.security.network.server`.
  - *What it answers* (`AndroidWiFiRouter`): a random 128-bit token (base64url) is the first path segment; only `GET` (else 405); `/<token>/` is the page, `/<token>/file/<index>` and `/<token>/preview/<index>` the batch's files by their index (never a path from the request). A wrong token, an expired one and any other path are the same 404. Files go as `application/octet-stream` with `Content-Disposition: attachment` (`<title>.mpkg`, unique within the batch), `Content-Length`, an ETag, and single `Range`s (206, 416, `If-Range`) so a download resumes.
  - *Limits*: 32 connections, 8 per device, a request budget per device (120 at once, 2 a second after, then 429), 10 s for a request's headers (16 KB at most), and a device that asks for 20 missing paths is turned away until the session ends.
  - *Lifetime*: the token and the listener end when the sheet closes, after 15 minutes (the sheet counts down), or when a new MCP session replaces the old one; "Send Again" makes a new token.
  - *The page* (`AndroidWiFiPage`): one responsive HTML page, inline CSS and a nonce'd inline script (CSP `default-src 'none'`), no outside resources: each package's preview, title, type (Scene (Dynamic), Scene (Pre-Rendered), Video) and size with a Download button, "Download All" (one after another, 1.5 s apart; the page says the browser asks once to allow several downloads), and the import steps.
  - *The sheet*: the QR code (`AndroidWiFiQRCode`, CoreImage's `CIQRCodeGenerator`) and the URL, each file's progress and the devices that downloaded it, help for the firewall prompt and client isolation, and "Save to Folder…" when the Mac has no local-network address.

## Lock screen and screen saver

How to use them: [`screen-saver.md`](screen-saver.md).

- **Desktop pictures** (`App/DesktopPictureController`, `DesktopPictureSync`, `DesktopPicturePlan`, `DesktopPictureComposer`, `LockScreenPicture`; on while Settings › General › "Show Wallpaper on Lock Screen" or the menu bar tint is on, both of which read the system desktop picture). Each display's picture is a picture of what that display shows: its own wallpaper, a clone's (mirrored when flipped), its part of a stretch's canvas, a split display's regions, each with its display options (offset, zoom, flip), on black. The source is a scene's loading snapshot (`SceneLoadingSnapshotStore`, nothing new is captured), a video's frame or a web page's snapshot (`DisplayPictureLoader`), or the wallpaper's preview until there is one. A plain display copies its snapshot; anything else is drawn at the display's size. The copy lives at `<Caches>/Open Wallpaper Engine/DesktopSnapshots/lock-<display>-<a|b>.<heic|jpg>`, out of reach of every cache trim, and stays after quitting (pictures are per Space, and macOS sets the current Space's only). A changed wallpaper, layout, display option or snapshot updates the displays whose picture changes; a Space change, a wake or a display change shows the current picture again. The picture each display showed first is recorded per display and put back, if it still exists, when both settings are off or the app quits.
- **Screen saver** (`ScreenSaver/`, Settings › Plugins › Screen Saver, off by default). While on, the current scene, web or WebM video wallpaper's loop video is made for each display's pixel size by the helper run `--render-screensaver-loop` (`ScreenSaverLoopRenderer`, `ScreenSaverWebLoopRecorder`): a `.library` job on the `PreparationPool` under the power policy, in its own process at background priority, HEVC through `AVAssetWriter`, scripts seeing `engine.isScreensaver()` true.
  - **Loop length.** With only periodic motion (timelines, sprite sheets; no particles or scripts) the loop is the least common multiple of the periods, at most 30 s, a whole number of frames at 30, 24 or 25 fps (never above 30), and frame N is checked against frame 0 (`ScreenSaverLoopLength`). Otherwise up to 30 s is rendered at 30 fps and the loop ends before the frame most like frame 0 after 5 s, compared at 64×36 (`ScreenSaverSeamFinder`), with a 0.25 s crossfade when that seam is still visible.
  - **Layout** (`ScreenSaverLayoutPlan`, from `ScreenSaverDisplayLayout` and what the displays show, re-planned when either changes, `ScreenSaverPlugin.observe`). Per display: a loop per distinct wallpaper and properties, displays sharing one recording at the largest of their sizes (with "Same as wallpaper", a clone group plays its source's loop and a stretch group a stretch loop). Clone: the source's loop on every display. Stretch: one loop recorded at the canvas's size (`DisplayCanvas`, at most 8192 pixels a side), and each display's manifest entry names the display (`displays`, its identity) and its rect of the video (`crop`); the saver sizes its player layer to the whole video and offsets it so the rect fills the screen. A video wallpaper plays its own file in every layout, cropped for a stretch. The fields are optional, so an older saver still plays a manifest (uncropped). A split display plays its first region's wallpaper.
  - **Video wallpapers.** No render: the wallpaper's own MP4/MOV (H.264 or HEVC) goes in the folder as a hard link, else a symbolic link, or as its repaired copy when its track is `hev1`/`avc3` (`ScreenSaverVideoSource`); the manifest entry takes the track's size and the playback speed, and the saver loops it with `AVPlayerLooper`, muted. WebM is recorded as a web page (below).
  - **Web pages and WebM videos** (`ScreenSaverWebLoopRecorder`, same helper argument plus the user properties as JSON). The page loads in an offscreen `WKWebView` of the display's size in points, configured as on the desktop (scheme handler and WE patches, pause script, WE web API bridge, properties and FPS, a silent audio feed, muted). Its time is stepped: an injected virtual clock drives `performance.now`, `Date.now`, animation frames, timers, CSS animations and `<video>` time 1/30 s per frame, and `takeSnapshot` captures each frame (no Screen Recording permission; the per-frame time is logged). The loop is always the seam finder's search; frames are kept in a near-lossless intermediate video and re-encoded into the loop. A page that doesn't load exits 3 and the Details pane says Not Available with the reason. Clocks a page draws itself aren't hidden. Application wallpapers stay ineligible.
  - **Storage.** The videos and `current.json` (`ScreenSaverManifest`) go in `~/Library/Application Support/Open Wallpaper Engine/ScreenSaver`: macOS stops the app writing into the saver host's (`legacyScreenSaver`) container, and that host may read any path. Each video is named by wallpaper and content, a hash of its user properties, the pixel size and `ScreenSaverVideoStore.revision`; anything the manifest no longer lists is removed.
  - **Screen Saver mode** (the Scene Editor (Live)'s middle tab, scenes only). An isolated session (`ScreenSaverEditorModel.purpose`) runs the wallpaper's screen saver version in its private instance: the sidebar's visibility switches, the layer adjustments and the user properties edit it, never the desktop's stores. Its values are saved per wallpaper as the screen saver's own choices (`ScreenSaverSettingsStore`, `ScreenSaverValues.<identity>` in `UserDefaults.app`) as they change, from the first change on (until then the mode starts from the wallpaper's values), and the next session and every recording of that wallpaper start from them. An always-shown note says the screen saver is a video, so clocks, dates, media info and audio-reactive parts show the moment it was recorded. **Record and Set as Screen Saver** (`ScreenSaverRecordingService`, `ScreenSaverRecorder`) runs the same helper with `--screensaver-recording`: the scene loads with the session's values in the helper's scratch defaults and draws its clock layers (the layer choices decide), at the size the plugin would use, into a staging folder in Caches; the store then moves it into the folder under a new name (`…-rec<time>.mov`), rewrites the manifest atomically to list it, and only then removes the previous video (`ScreenSaverVideoInstalling`), so the saver never sees a missing or partial file. The recording becomes the selection (`ScreenSaverSelection`): while it is set, the plugin renders nothing for the desktop's wallpaper; Stop Using as Screen Saver goes back to it, and turning the plugin off clears it with the videos. Preview Recording loops the installed video in the mode's frame.
  - **Daily re-recording** (off by default, `ScreenSaverSchedule`, `ScreenSaverDailyScheduler`). "Re-record every day at [time]" records the selection again with its saved choices, so the date and time in it are that day's. A one-shot `Timer` (a minute's tolerance) is armed for the next time, and a check at launch, at wake and on clock, time zone or day changes runs a time missed while asleep or quit, once. The time is a local wall-clock time: a skipped time (spring change) runs at the next time that exists, a repeated one (autumn) once, and after a time zone change it follows the new zone. Runs are at background priority and wait while on battery below 30 % or critically hot (`PowerPolicy.allowsScheduledRecording`), retrying every 30 minutes; each run, skip and result is logged. The app has no LaunchAgent, so nothing runs while it is quit; the next launch catches up.
  - **Saver.** The `OpenWallpaperEngineSaver` target (`OWESaverView`: a `ScreenSaverView` with an `AVPlayerLayer` and `AVPlayerLooper`) is embedded in the app and copied to `~/Library/Screen Savers`; the app then opens the Screen Saver settings for the user to choose it and changes no system setting itself. Turning the plugin off stops rendering and removes the saver and the videos.
- **Isolation.** An isolated copy never sets the desktop picture, installs or removes the saver, or writes where the saver reads (its videos go under its own support folder).

## Invariants

- **WE semantics, not approximations.** Wallpaper Engine's shaders and effect definitions are the reference. Hand-written "native" effects and name/regex heuristics are technical debt to delete, not a pattern to extend (see [`CONTRIBUTING.md`](../CONTRIBUTING.md)).
- **Per-wallpaper state.** State belongs to a wallpaper *instance* (one per wallpaper and set of user properties, shared by the displays showing it), never to a process-wide singleton.
- **Loud failure.** A shader that fails to build, a layer that can't be decoded, or a script that throws is logged once, with the wallpaper, layer and reason.
- **Honest caches.** Everything derived from inputs (shader translations, `.metallib`s, parsed scenes) is keyed on its inputs *and* the version of the code that produced it.
